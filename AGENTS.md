# AGENTS.md

Контекст и договоренности по проекту plc-esp2 (рабочие заметки)

## Важные наблюдения и договоренности

- В логах для параметров использовать : вместо =.\n- Регистрацию коллбеков отображения веб-страниц делать ПОСЛЕ регистрации всех функциональных коллбеков/обработчиков.
- Файлы с русским текстом сохранять в UTF-8, иначе проблемы с кириллицей (mojibake) и правками.
- При создании больших буферов и кэшей предлагать использовать PSRAM.
- Если в веб-страницах есть русские строки, их лучше править через команды записи целиком (Set-Content), чтобы не ломалась кодировка.
- В интерфейсе дисплея все поля ограничиваем 3 символами; ошибки показываем как `ERR` (3 символа). 4-й символ заполняется пробелом.
- Время на дисплее отрисовывается в 2 слотах (часы и минуты) — это осознанное ограничение по 3 символам.
- Для температуры: если значение <= -10, знак градуса не рисуется (чтобы влезть в 3 символа).
- При ошибках получения данных (кэш/запросы) в соответствующих полях дисплея выводится `ERR`.

## Изменения по стеку (архитектура и поведение)

- StackCache перемещён в App как отдельный член. Потребителям (WebInterface и др.) передаётся ссылка/указатель через `setStackCache()`.
- Инициализация кэша перенесена туда, где инициализируется сеть/стек (App::begin); из WebInterface удалён `initStackCacheAllocations()`.
- Для слейва добавлены отдельные кэши (sockets/lights/tanks/septic/meteo) с выделением памяти в PSRAM, опрос — только по запросу (для веба/дисплея).

## Фоллбек-режим стека

- Добавлен флаг фоллбека и адрес fallback-хоста в конфиг, настраиваются в Web (Стек) и CLI.
- При потере связи с мастером слейв переходит в режим master (если включен fallback и НЕ задан fallback_host).
- Если задан fallback_host — локальный master НЕ поднимается, слейв переключается на другого мастера.
- Логи: переход в fallback master и выход из него, а также лог «Role switch: master/slave».
- MASTER_LED_PIN: светодиод горит в режиме master (включая fallback) и гаснет в режиме slave.

## Признак «контроллер/модуль»

- Для слейва есть флаг `slave_controller` (по умолчанию true).
- Этот флаг передаётся через caps в StackHello; хранится в StackMaster.
- В Telegram и Cloud списках устройств показываются только узлы с `slave_controller=true`.
- В веб-странице Стек добавлена колонка «Тип» (Контроллер/Модуль).

## Веб-страница «Стек»

- Для роли master скрываются поля, относящиеся к slave.
- Русифицированы подписи, сокращены длинные тексты:
  - «Резервный мастер» + «Включить»
  - «Хост/IP резервного мастера»
  - «Слейв-контроллер» и т.п.

## Повторяющиеся ошибки/грабли

- Ошибка таб-комплишена CLI: при добавлении команд нужно обновлять размер массива `std::array`.
- Кодировка веб-страниц: редактирование через apply_patch может ломать UTF-8.
- plc-cloud: если даже в приватном окне видны кракозябры, проверять не только `ui.js`, но и `index.html`/`main.js` по HTTP (`curl -o ... http://host:3000/...`), потому что проблема может быть в статическом HTML, а не в runtime-рендере.
- plc-cloud: для Express static принудительно отдавать `charset=utf-8` для `.html/.js/.css/.json` и отключать кэш текстовой статики (`Cache-Control: no-store`), иначе браузер может продолжать показывать старую битую версию даже после `Ctrl+F5`.
- plc-cloud: PowerShell может искажать кириллицу в консольном выводе; для проверки реального содержимого файла/HTTP-ответа смотреть файл через Python (`read_text(encoding='utf-8')` + `encode('unicode_escape')`), а не полагаться на обычный `Get-Content` или redirect.
- При изменениях в Stack/CLI/Web важно синхронизировать:
  - config (ConfigsManager)
  - web формы + обработчики
  - CLI команды + help
  - README

## FreeRTOS / TaskBinder: текущее состояние

- Перенос runtime на FreeRTOS через `TaskBinder` завершён; `TaskManager` удалён.
- Текущая цель архитектуры:
  - короткий и детерминированный `control_loop`;
  - изоляция сетевых/блокирующих операций в фоновых RTOS-задачах;
  - минимальный и предсказуемый `App::loop()`.

### Текущий состав RTOS-задач

- Сеть/интеграции:
  - `network_loop`
  - `console_loop`
  - `wifi`
  - `gsm`
  - `cloud`
  - `telegram`
  - `meteo_history`
- Контроль и I/O:
  - `control_loop`
  - `plc_scan`
  - `extender`
  - `display`
  - `plc`
- Stack:
  - `stack_evt` (`taskPost/taskFlush`) через очередь.

### Что осталось в основном loop

- `App::loop()` сейчас выполняет только `runStackPre(stack)` (и опциональные GPIO-метрики под флагом).
- `notifyStackPostNetwork()` вызывается из RTOS-задачи `network_loop`.
- Прямых вызовов `network.loop()/console.loop()/plc_scan.tick()` из `App::loop()` больше нет.

### Архитектурные договорённости по RTOS

- Не плодить отдельные RTOS-задачи на каждое чтение GPIO.
- Для быстрых контроллеров предпочтителен **один общий `control_loop`**, а не десяток параллельных задач с гонками за `Controllers/Gpio`.
- `stack_evt` должен работать через очередь, а не через прямой вызов `taskPost/taskFlush` из `App::loop`.
- Для `stack_evt` добавлен флаг pending:
  - не надо заново посылать уведомление, если предыдущее ещё не обработано;
  - флаг реализован атомарно (`std::atomic`), не через `volatile bool`.
- Отдельные задачи оправданы для:
  - network / cloud / telegram / gsm;
  - console loop;
  - display;
  - plc scan;
  - extender / I/O-обвязки;
  - meteo history;
  - plc background.

### Debug и метрики RTOS

- Диагностический флаг:
  - `TASK_BINDER_RTOS_DEBUG`
  - задаётся через `platformio.ini`, а не hardcode в `TaskBinder`.
- Для появления RTOS debug-логов нужен и уровень логгера:
  - `LOGGER_LEVEL=4`
- Текущие RTOS-метрики логируются тегом `RTOS` и содержат:
  - `exec_us`
  - `avg_us`
  - `max_us`
  - `wavg_us`
  - `wmax_us`
  - `cnt`
  - `hwm`
  - `min_hwm`
- `wavg_us/wmax_us` — скользящее окно, более полезное, чем глобальный `max_us`, который может быть «испорчен» старым единичным пиком.

### Практические выводы по метрикам

- Нормальная картина:
  - `stack_evt`, `wifi`, `gsm` — десятки микросекунд;
  - `cloud` — обычно сотни микросекунд, иногда миллисекундные пики;
  - `telegram` и `meteo_history` могут иметь секундные пики из-за сети/FS.
- Если реле переключаются без микролагов, а `stack_evt/control` короткие — перенос сделан правильно, даже если `telegram/cloud` иногда подвисают на секунды.

### Логгер и RTOS

- После появления нескольких RTOS-задач вывод в лог надо считать многопоточным.
- В `Logger` добавлен mutex для сериализации вывода и recent-buffer.
- Если строки в логах всё ещё рвутся:
  - проверять прямые `Serial.print`/`printf` вне `Logger`;
  - проверять сторонние библиотеки, которые пишут в UART напрямую;
  - помнить, что `logISR` и сторонний вывод могут обходить общий lock.

### Антипаттерны для дальнейшего переноса

- Не выносить каждую розетку/датчик/кнопку в отдельную RTOS-задачу.
- Не переносить «чтение GPIO» как самостоятельную цель — проблема обычно не в GPIO, а в блокирующем соседнем коде.
- Не разносить controller logic по множеству задач без явной модели синхронизации.
- Не слать `stack_evt` notify на каждом витке loop без pending-защиты.

### Что смотреть после новых переносов

- Логи `RTOS`:
  - рост `wmax_us` у `control`
  - уменьшение `hwm/min_hwm`
  - `network`/`stack_evt` (не растёт ли latency post-network фазы)
  - всплески у `cloud` во время reconnect
  - всплески у `telegram` во время long-poll / reconnect
- Если появляются артефакты в логах — сначала проверять потокобезопасность логгера, а не сами метрики.

## I2C/extender/выходы: текущее состояние надёжности

- `I2CManager`:
  - при `probeAddress`-ошибке пытается восстановить шину (clock pulses + STOP) и повторить probe;
  - на ESP32 для `Wire` включён timeout (`setTimeOut(50)`).
- `RTC`:
  - хранит `_ready`;
  - при I2C-сбое сбрасывает ready и при следующем обращении делает повторный `begin()`.
- `Display`:
  - при `Time`-слоте и ошибке `RTC` выводит `ERR` вместо пустого/битого значения;
  - custom-символы и backlight инициализируются в task под lock, а не в раннем begin без проверки шины.
- `Extender`:
  - runtime I/O fail -> устройство помечается `missing`;
  - включается ускоренный перескан (`fast_rescan_interval_ms`) до восстановления.
- `PortIO`:
  - добавлен режим `setOutputsEnabled(false/true)`;
  - выходы не применяются физически до явного разрешения;
  - в `App::begin()` порядок: `controllers.restoreFromStorage()` -> `io.applyOutputs()` -> `portio.setOutputsEnabled(true)`.
## Стековые кэши: структура работы

- Два уровня кэшей:
  - Master: `StackCache` (в App), хранит кэши по нодам для sockets/lights/meteo/thermo/tanks/septic/security.
  - Slave: `StackSlaveHandler` держит `remote*Cache` (sockets/lights/meteo/thermo/tanks/septic/security) и запрашивает данные у мастера.
- Обновление кэша на мастере:
  - Только через ответы на `CmdGet` (`Ack/Err`) от слейвов.
  - Поля кэша: `has_data`, `pending`, `last_ok`, `last_error`, `updated_ms`, `item_count`, `items[]`.
  - Для `Security` в кэше хранится и статус: `enabled/armed/alarm`, плюс сенсоры.
- Обновление кэша на слейве:
  - Через ответы мастера на `CmdGet` (remote‑кэши).
  - Логика и флаги аналогичны master‑кэшу.
- Инициирование запросов:
  - В отображении (дисплей/веб) при отсутствии данных вызываются `request*`.
  - Для актуальности на мастере в фоне работает `pollStackCaches_()` — по очереди опрашивает ноды (security/septic/tanks/meteo).
- Дисплей:
  - Для `master` берёт данные из `StackCache`.
  - Для `slave` берёт данные из `remote*Cache` (через мастера).
- Алармы:
  - На мастере алермы пересчитываются по кэшу и локальным данным.
  - На слейве удалённые алермы не учитываются (только локальные).

## Дисплей: источники данных и режимы

- Общая схема:
  - В каждом слоте дисплея хранится `kind/field/index/node_id`.
  - `node_id = 0` означает локальные данные.
  - `node_id != 0` означает данные другого юнита.
- Режим master:
  - Данные других юнитов берутся из `StackCache` (master‑кэши).
  - Если данных нет, инициируется `request*` (CmdGet) к слейву.
  - Ошибки получения данных показываются как `ERR`.
- Режим slave:
  - Данные других юнитов берутся из `StackSlaveHandler::remote*Cache`.
  - При отсутствии данных инициируется запрос к мастеру (`requestRemote*`).
  - Ошибки получения данных показываются как `ERR`.
- Поддерживаемые слоты (remote):
  - `Socket`, `Light`, `Meteo`, `Thermo`, `Tank`, `Septic`, `Security` — все имеют remote‑режим.
  - `Security`: отображает `ARM`/`DIS` (armed) по кэшу.
  - `Thermo`: отображает статус `IDL/HET/COL` по `power_on/heat_on/cool_on`.
- Локальные источники:
  - `Security` — `control.controllers.security().armed()`
  - `Meteo` — `MeteoController::state(...)`
  - `Thermo` — `ThermoController::state(...)`
  - `Tank` — `TankController::state(...)`
  - `Septic` — `SepticController::stateByIndex(...)`

## Алармы: структура и логика

- Базовая структура в `PlcControl`:
  - `AlarmModule` = `Sockets/Lights/Meteo/Thermo/Tanks/Septic/Security/Ring`.
  - `_alarm_mask` — маска “модуль имеет аларм”.
  - `_alarm_detail_mask[mod]` — детальная маска (датчик/бак/канал) внутри модуля.
  - `_alarm_unit_mask[mod]` — маска по юнитам (stack node index) внутри модуля.
  - LED мигает, если есть любой активный бит (`alarm_mask | detail_any | unit_any`).
- Слои логики:
  - Детальные/юнит‑маски автоматически поднимают/снимают модульную маску.
  - Для `unit_mask` используется индекс ноды в `StackMaster` (0..31).
- Где выставляются/очищаются:
  - **Tanks**
    - Локально: `updateTankAlarms_()` — если `!levels_ok || empty` → детальный бит.
    - Remote (только master): берётся из `stack_cache.tanksCache` и ставит детальный + unit‑бит.
  - **Septic**
    - Локально: `updateSepticAlarms_()` — `st->alarm` → детальный бит.
    - Remote (только master): из `stack_cache.septicCache` + unit‑бит.
  - **Security**
    - Локально: `onSecurityDetect_()` — если `!silent` → детальный бит.
    - Очистка: `onSecurityClearDetect_()` → сброс detail/unit.
    - Remote (только master): по `StackCache` и по входящим `alarm` (stack frame) ставится detail+unit.
  - **Meteo**
    - Локально: `updateMeteoAlarms_()` — если `!ok` → детальный бит.
    - Remote (только master): из `stack_cache.meteoCache` + unit‑бит.
  - **Thermo**
    - Сейчас только для отображения; алармы не заведены.
  - **Sockets/Lights/Ring**
    - Алармы не используются, только модульные/детальные поля зарезервированы.
- Важные ограничения:
  - На **slave** удалённые алармы не учитываются (только локальные).
  - На **master** удалённые алармы пересчитываются по кэшу и входящим событиям.

## Контроллеры: поведение и источники данных

- **Sockets (Розетки)**
  - Конфиги: `SocketController::configByIndex`, `lightConfigByIndex`.
  - Стейт: `state(id)`, `lightState(id)` → `relay_on`.
  - Стек: master — `StackCache::socketsCache/lightsCache`, slave — `remoteSocketsCache/remoteLightsCache`.
  - Дисплей: показывает `ON/OFF`.
  - Алармы: не используются.

- **Meteo (Метео)**
  - Конфиги: сенсоры `configByIndex`; поддержка remote‑источника (`source_node_id/source_sensor_id`).
  - Стейт: `state(id)` → `ok/has_temp/has_humidity/temp_c/humidity`.
  - Логи: ошибки/восстановления логируются по смене состояния (без спама).
  - Стек: master — `StackCache::meteoCache`, slave — `remoteMeteoCache`.
  - Дисплей: temp/hum, ошибки → `ERR`.
  - Алармы: если `!ok` (локально + remote через кэш).

- **Thermo (Термо)**
  - Конфиги: `configByIndex` (mode, target, hyst, ports, sensor).
  - Стейт: `power_on/heat_on/cool_on`.
  - Стек: master — `StackCache::thermoCache`, slave — `remoteThermoCache`.
  - Дисплей: `IDL/HET/COL` по `power_on/heat_on/cool_on`.
  - Алармы: не заведены.

- **Tanks (Баки)**
  - Конфиги: `configByIndex` (id, ports, enabled).
  - Стейт: `level_low/mid/full`, `levels_ok`, `valve_on`, `pump_on`.
  - Стек: master — `StackCache::tanksCache`, slave — `remoteTanksCache`.
  - Дисплей: `FULL/MID/LOW/EMP`.
  - Алармы: `!levels_ok || empty` → detail; remote (master) → detail + unit.

- **Septic (Септик)**
  - Конфиги: `configByIndex` (monitoring_on, ports).
  - Стейт: `warning/alarm`, реле warning/alarm.
  - Стек: master — `StackCache::septicCache`, slave — `remoteSepticCache`.
  - Дисплей: `ALRM/WARN/OK`.
  - Алармы: `alarm` → detail; remote (master) → detail + unit.

- **Security (Охрана)**
  - Конфиги: `configByIndex` (silent, type, port, name).
  - Стейт: `is_detect`, `armed`, `alarm_on`.
  - Стек: master — `StackCache::securityCache` (сенсоры + `enabled/armed/alarm`), slave — `remoteSecurityCache`.
  - Дисплей: `ARM/DIS` по `armed`.
  - Алармы: `!silent` детекты → detail; `clearDetect` → сброс; remote (master) → detail + unit.

- **Ring (Звонок)**
  - Стейт: `relay_on`.
  - Стек: есть команды `button/set`, отображение на дисплее не предусмотрено.
  - Алармы: не используются.

- **PLC/RTC**
  - PLC: температуры (board/cpu), вентиляторы, alarm LED.
  - RTC: дата/время/температура.

## Стек: архитектура и обмен

- **Роли**
  - Master — агрегирует данные, держит `StackCache`, раздаёт web/дисплей/alarms.
  - Slave — подключается к мастеру, использует `StackSlaveHandler` для обработки команд и отдачи данных.
  - Fallback — при потере мастера может стать мастером (если включено и нет `fallback_host`).

- **Транспорт и типы сообщений**
  - Используются `StackMsgType::CmdGet/CmdSet/Ack/Err`.
  - Master отправляет `CmdGet` слейву для чтения состояния/конфигов.
  - Slave отвечает `Ack` (ok + data) или `Err` (error).

- **Фичи (StackFeature)**
  - Покрывают подсистемы: `Sockets`, `Lights`, `Meteo`, `Thermo`, `Tanks`, `Septic`, `Security`, `Ring`, `PlcStatus`, `Rtc`, и др.
  - Каждая фича имеет набор `action` (`get`, `set`, `status`, `status_req`, `button`, и т.п.).

- **StackCache (на мастере)**
  - Хранит кэши по нодам для основных фич.
  - Обновляется только по ответам `Ack/Err`.
  - Используется вебом/дисплеем/alarms.

- **StackSlaveHandler (на слейве)**
  - Получает команды от мастера, отдаёт ответы.
  - Держит remote‑кэши для отображения данных с других узлов через мастера.
  - В режиме слейва, при необходимости, запрашивает у мастера (`requestRemote*`).

- **Идентификация узлов**
  - `node_id` используется как уникальный идентификатор.
  - На мастере хранится имя и IP (для UI/логов).
  - Индекс узла в `StackMaster` используется для unit‑alarm масок.

- **Обновление данных**
  - Мастер выполняет периодический `pollStackCaches_()` (по очереди опрашивает ноды).
  - В UI/дисплее при отсутствии данных инициируется запрос `request*`.

- **Безопасность**
  - Поддерживается `stackApiKey` (проверяется в master‑обработчике запросов).

- **Ограничения**
  - На слейве удалённые алармы не учитываются.
- Remote‑дисплей работает через кэш (master‑cache или remote‑cache).

## Облако и proto.json

- В проекте есть `proto.json` — единый JSON‑протокол, используемый и в прошивке (C++), и в облаке (например, Node.js).
- `proto.json` служит источником правды для:
  - формата команд/ответов;
  - структуры данных (features/parts/actions);
  - совместимости версии протокола.
- Любые изменения в протоколе должны синхронно отражаться в прошивке и в облаке.
- `CloudClient` не должен зависеть напрямую от `WebSocketsClient` или `HTTPClient`; transport-специфика выносится в `CloudTransport`.
- Текущая рабочая реализация транспорта: `CloudWsTransport`.
- `CloudHttpTransport` уже участвует в конфиге, CLI и Web как selectable transport, но без серверных device HTTP endpoints остаётся placeholder, а не полноценной заменой WS.
- При доработке облака разделять слои жёстко:
  - `CloudClient` — protocol/session/business logic;
  - `CloudTransport` — connect/disconnect/send/poll и события транспорта.
- При смене транспорта нельзя дублировать или форкать cloud-протокол; transport меняется под `CloudClient`, а не наоборот.
- Если добавляется новый transport, нужно синхронно обновлять:
  - `ConfigsManager` / runtime apply
  - Web `/cloud`
  - CLI `config cloud`
  - README
- Контроллеры не должны зависеть от `TelegramBot`/`TelegramAllowedUsersProvider` для cloud-нотификаций.
- Controller notifications публикуются как доменные `event` через очередь `CloudClient`, а не отправляются из контроллеров напрямую.
- Telegram-уведомления для cloud-сценариев формируются в `plc-cloud` из `event/last_event`, а не в прошивке.
- Исключение: локальные GSM/SMS/Call-оповещения (например, `Security`) могут оставаться в прошивке.
- Для stack-событий master публикует scoped cloud event с `unit: "stack"` и `node_id`; в `payload.data` дополнительно должен быть человекочитаемый `source_name` (имя слейва).
- Для локальных cloud events `payload.data.source_name` должен содержать имя текущего PLC.
- Очередь cloud events сейчас `64` элементов; повторяющиеся `sockets.state`/`lights.state` для одного и того же `source + id` нужно схлопывать, а не накапливать.
- Cloud-диагностика в логах:
  - `Notify send: ...` — событие реально отправлено в cloud transport;
  - `Event queue full, drop oldest` — очередь переполнена;
  - `Stack cmd error: ...` — slave вернул `Err`;
  - `STACK Master tx busy/short write` и `STACK Unit tx busy/short write` — stack transport не принял frame целиком.
- Для stack `CmdSet` нельзя считать отправку успешной без проверки результата `sendTo()/write()`: pending/ack нужно регистрировать только после успешной физической отправки frame.

## Кейс: рассинхрон Thermo (stack web tile) и шаблон для будущих контроллеров

- Симптомы (как проявлялось):
  - Переключатель `Active` менялся сразу, реле физически щёлкало, но иконка/индикатор/статус на плитке оставались в старом или сером состоянии.
  - Иногда обновлялось только после второго нажатия или `F5`.
  - В отдельных циклах появлялось краткое `Термо отсутствует` после `set`.

- Почему это произошло (корневые причины):
  - `Thermo` в web работал через `submit + reload`, в отличие от `Sockets` (у которых быстрый `fetch /toggle`).
  - `Ack` от `CmdSet` мог интерпретироваться как источник обновления `get`-кэша некорректно.
  - На мастере при частичном обновлении thermo-кэша использовалась логика с `|` для bool-полей: `false` мог не применяться.
  - `state` мог возвращать устаревший кэш (или кэш в `pending`) и фронт принимал это как финальное состояние.
  - На фронте был риск гонки: старый poll-ответ перетирал результат нового клика.

- Что зафиксировано в реализации:
  - Backend:
    - Добавлен быстрый endpoint: `GET/POST /thermo/toggle`.
    - Для `stack`:
      - `action=on/off/toggle` отправляет `CmdSet` на нужный `node_id`.
      - После `set` инициируется `requestThermo(node_id)`.
      - Ответ на `set` для web: `pending` (не финальное состояние).
      - `action=state` возвращает `pending`, если кэш `pending`/stale/empty; JSON-состояние возвращается только когда кэш свежий.
    - Для `local`: `thermo.setPower/togglePower`, `action=state` отдаёт JSON с фактическим `power/heat/cool`.
    - На слейве `Thermo set` возвращает `Ack` с `items` по изменённым элементам (не пустой ack).
    - В `StackCache` добавлен отдельный путь обработки `Thermo action=set` (точечный апдейт item по `id`), отделённый от `get`.
    - Исправлено обновление bool/числовых полей в кэше без `|`-слияния (иначе `false` мог теряться).
  - Frontend (`web_interface_thermo`):
    - Переключатель power переведён на `fetch('/thermo/toggle')` вместо полного submit.
    - После toggle включён `state`-poll с ретраями.
    - Poll защищён от гонок через `reqId` (устаревшие ответы не применяются).
    - Для команды `ON` финализация UI не останавливается на промежуточном состоянии, пока не получено рабочее `heat/cool` или не вышел лимит попыток.

- Практический шаблон для будущих контроллеров (рекомендуемый стандарт):
  - 1) UI-канал:
    - Для частых действий (toggle, arm/disarm, valve on/off) использовать отдельный быстрый endpoint `*/toggle` (JSON/plain), а не submit всей формы.
  - 2) Ответ сервера на toggle:
    - Если фактическое состояние ещё не подтверждено кэшем, возвращать `pending`.
    - Не отдавать устаревший state как финальный.
  - 3) Cache-sync:
    - После `CmdSet` обязательно запускать `request*` для соответствующей feature/node.
    - В кэше иметь отдельную обработку `action=set` (частичный апдейт), не смешивать с `get`-сборкой списка.
  - 4) Frontend state-poll:
    - После toggle запускать короткий polling `action=state`.
    - Защита от гонок обязательна (`request_id`/`nonce`, игнор старых ответов).
    - Останавливать poll только когда состояние валидно по правилам контроллера.
  - 5) Условия валидности финального состояния (controller-specific):
    - Для Thermo: при ожидаемом `ON` считать «готово» только когда есть подтверждённый `heat_on || cool_on` (или достижение timeout-порога).
    - Для Sockets/Lights: достаточно `state on/off`.
  - 6) UX:
    - `pending` не должен визуально затирать уже подтверждённое новое состояние.
    - Ошибка toggle должна откатывать локальный переключатель.
  - 7) Протокол:
    - Для `CmdSet` полезно возвращать компактный `Ack` с изменёнными item-полями (`id + state`), чтобы мастер мог быстро синхронизировать кэш.
  - 8) Логи/диагностика:
    - На debug-этапе полезны `req sent/skip/pending age`, но перед релизом шумные `Rx/Tx` логи нужно отключать.

- Антипаттерны (чего избегать):
  - Обновлять UI сразу «оптимистично» без дальнейшей верификации state.
  - Считать первый же `state` после `set` финальным, если кэш ещё `pending`.
  - Смешивать `Ack set` и `Ack get` без проверки `action`.
  - Сливать bool-поля в кэше через `|` при частичном апдейте.

## Кейс: Stack Sync не появляется + «постоянное ожидание устройств»

- Симптомы:
  - На мастере в логах есть `Unit online`, `Tx ... get/prearm`, но нет (или почти нет) `Sync slave unit ...`.
  - Для части контроллеров (особенно Thermo/Tanks/Septic/Security) долго висит состояние ожидания.
  - Иногда данные появляются только после открытия конкретной вкладки в web или после перезапуска обоих устройств.
  - В debug-периоде наблюдались повторяющиеся `Thermo req sent/skip pending ...` без устойчивого перехода в «ready».

- Почему так происходило:
  - Фоновый опрос кэшей на мастере делал «пакет» запросов по всем feature за тик/узел.
  - Для медленных/частичных ответов это приводило к конкуренции pending-состояний и starvation отдельных feature.
  - В результате часть feature не доходила до стабильного `has_data/last_ok`, поэтому `Sync`-логов по ним не было.
  - Дополнительно для Thermo был рассинхрон обработки `Ack set/get`:
    - `Ack set` мог неверно участвовать в пути `get`,
    - частичный апдейт кэша с `|` для bool мог не применять `false`.

- Ключевые исправления (что внедрено):
  - `App::pollStackCaches_()` переведён на round-robin по feature:
    - за тик отправляется один запрос для одной feature (на текущий node),
    - индекс feature циклически ротируется.
  - Это убрало «залп» запросов и снизило перманентный pending.
  - Для Thermo:
    - в `StackCache` разделены пути обработки `action=get` и `action=set`,
    - добавлен корректный частичный апдейт по `set` (без потери `false`),
    - на слейве `Thermo set` формирует содержательный `Ack` с item-state.

- Как диагностировать в будущем:
  - Проверять цепочку:
    - `Unit online` -> `request*` -> `Ack/Err` -> `cache.has_data/last_ok` -> `Sync ...`.
  - Если есть `request` и нет `Sync`:
    - смотреть `pending` и `updated_ms` по feature/node,
    - смотреть action в ack (`get` vs `set`), не смешивается ли обработка.
  - Проверять, не вызывается ли массовый опрос всех feature за один тик.

- Принцип устойчивого опроса для новых feature:
  - Опрос только в round-robin, по одной feature за тик/узел.
  - Таймаут pending обязателен (сброс зависшего pending).
  - `Ack set` и `Ack get` обрабатываются раздельно.
  - `Sync`-лог должен формироваться только по факту свежего и валидного кэша.
  - UI «ожидание» должен опираться на `pending/stale`, а не на разовые optimistic-данные.

- Антипаттерны:
  - Отправлять 8-12 `CmdGet` подряд на каждую ноду в одном цикле.
  - Считать отсутствие `Sync` чисто UI-проблемой, не проверив cache state machine.
  - Пытаться лечить только увеличением интервалов без разделения `set/get` путей.



## Stack Ports / GPIO (slave -> master): баг неполных списков и финальное решение

Проблема проявлялась в вебе на master при настройке stack-устройств (сокеты/свет/термо и др.):
- списки GPIO на slave-карточках были пустыми;
- либо появлялись только после нескольких `F5`;
- либо отображалось только 1-3 порта (часто только реле);
- состав списка менялся от обновления к обновлению;
- списки могли исчезать на таймерном обновлении страницы и затем появляться снова.

### Симптомы в логах

Типичные признаки:
- `Drop rx frame: json parse failed type: 6 node: ... bytes: 1024`
- `Ports timeout finalize: node: ... items: N parts: X/Y`
- `Ports cache progress: ... items: ... parts: ...`
- `Stack ports options empty: node: ... has_cache: 1 has_data: 0 pending: 1`

Это означает, что ответы `Ports` либо слишком большие для одного stack frame (JSON упирается в лимит ~1024 байта),
либо multipart-части теряются/приходят неполно/не по порядку, а master пытается использовать частичный кэш.

### Корневая причина (что было не так)

Старый механизм `Ports get_state` на slave работал как burst multipart:
- слейв на один `CmdGet` отправлял подряд много `Ack`-частей (`part/parts/done`);
- при высокой нагрузке / параллельном обмене часть частей терялась или приходила в другом порядке;
- некоторые `Ack` были слишком большими (JSON ~= 1024 байта), что приводило к `json parse failed` на master;
- master иногда преждевременно финализировал кэш по `done`, даже если пришли не все части;
- при очередном запросе портов кэш очищался заранее, из-за чего веб на мгновение видел пустые списки (flicker).

Дополнительно была ошибка в сборке multipart-кэша:
- данные писались индексно (`items[id]`),
- затем выполнялась in-place compact-упаковка в начало массива,
- после чего следующие части снова писались по индексам и могли затирать уже упакованные данные.
Это давало эффект «схлопывания» списка до 1-2 элементов.

### Что сделано (финальное решение)

#### 1) Перевод `Ports` на page-based pull (offset/limit)

Вместо burst multipart внедрён page-based pull:
- master запрашивает страницы `Ports` последовательно (`offset/limit`);
- slave отвечает одной страницей за запрос;
- master после получения страницы запрашивает следующую (`next_offset`) до `done=true`.

Преимущества:
- нет длинного burst-а `Ack` подряд;
- меньше конкуренции в TCP/stack transport;
- проще контролировать размер ответа;
- выше стабильность доставки.

Ключевые поля ответа страницы:
- `ports` (массив элементов страницы)
- `offset`
- `limit`
- `total`
- `next_offset`
- `done`

#### 2) Compact payload (`brief=true`) для веб-селекторов GPIO

Для `Ports`-запросов с master добавлен `brief=true`:
- slave отправляет только поля, необходимые для селекторов GPIO:
  - `id`, `state`, `ptype`, `ctrl`, `used`, `ext`, `dev`, `pin`
- тяжелые строковые поля (`backend`, `loc`, `type`, `hw`) не отправляются в этом режиме.

Это резко уменьшает размер JSON и снижает риск упора в 1024 байта.

#### 3) Уменьшение page size

Даже с `brief=true` размер страницы может быть большим на некоторых профилях/платах.
Поэтому `Ports` page size на master уменьшен (финально до малого значения), чтобы гарантированно помещаться в frame.

Итоговый принцип:
- лучше больше маленьких страниц, чем редкие oversized `Ack` с `json parse failed`.

#### 4) Устойчивый кэш `Ports` на master

Исправления в `StackCache`:
- не финализировать кэш преждевременно;
- не очищать видимый кэш сразу при старте нового запроса (чтобы не было пустых списков в UI);
- очищать/пересобирать кэш только при получении первой страницы (`offset=0`);
- сохранять старые данные до прихода новой первой страницы;
- использовать `present[]`/индексное хранение в процессе сборки и compact только на финализации.

Это устранило:
- пропадание списков на таймерном обновлении;
- нестабильное количество элементов;
- “1-2 реле” вместо полного списка.

#### 5) Форс-обновление кэша портов после remote-save

После сохранения настроек stack-устройств (где меняются GPIO) master теперь принудительно обновляет `Ports` cache:
- `Sockets`
- `Lights`
- `Thermo` (после включения stack-save GPIO)

Используется helper `refreshStackPorts_(node_id)`:
- инвалидация кэша;
- новый page-based запрос.

Это нужно, чтобы селекторы сразу видели актуальную занятость GPIO (`used`) и не показывали старую картину.

### Что важно для Thermo (stack)

По `Thermo` дополнительно реализовано:
- отображение текущих GPIO со слейва в селекторах (`heat/cool/button`) через stack cache;
- сохранение новых GPIO по стеку на слейв;
- поддержка пустых GPIO (`-` / none -> invalid port);
- после сохранения — форс-обновление `Ports` cache.

Это устранило рассинхрон между UI и реальной конфигурацией слейва.

### Совместимость и обновление прошивок

После удаления fallback multipart для `Ports`:
- master ожидает только page-based формат (`offset/limit`);
- slave должен уметь отвечать page-based.

Следствие:
- для стабильной работы `Ports/GPIO` нужно обновлять **и master, и slave** до версии с page-based `Ports`.

Если обновлён только master (или только slave), возможны ошибки:
- пустые списки GPIO;
- `ports page fields missing`;
- отсутствие обновления кэша портов.

### Диагностика в будущем (если проблема вернётся)

Проверять по шагам:
1. Есть ли `Ports rx` / `Ports cache progress` / `Ports cache ready` в логах master.
2. Нет ли `Drop rx frame: json parse failed ... bytes: 1024`.
3. Нет ли `Ports timeout finalize` (если page-based уже внедрён, это тревожный признак).
4. При сохранении stack-конфига вызывается ли `refreshStackPorts_(node)`.
5. Совпадают ли версии master/slave по `Ports`-протоколу (page-based vs legacy).

### Правило на будущее для тяжёлых stack-ответов

Если feature потенциально отдаёт много элементов/полей:
- НЕ использовать burst multipart как основной путь;
- делать page-based pull (`offset/limit`) по инициативе master;
- предусматривать compact/brief payload для UI-задач;
- не очищать рабочий кэш до получения первой страницы нового снапшота;
- обновлять зависимые кэши после remote-save (если они влияют на UI-селекторы/валидацию).

## Кейс: два слейва в сети, но синхронизируется только один (конфликт `node_id`) + ускоренная первичная синхронизация

### Симптомы (как проявлялось)

- В сети физически два слейва, но в web/stack списке отображается только один.
- Синхронизация (`Sync slave unit ...`) идёт попеременно то для одного, то для другого устройства.
- В логах есть `Unit reconnected` без ожидаемой устойчивой работы двух нод.

После добавления диагностических логов стало видно:
- оба устройства выходили с одинаковым `node_id`;
- мастер постоянно вытеснял одну сессию другой.

Типичный лог:
- `Duplicate unit_id conflict: 0x... old: Огород ip: ... new: Баня ip: ...`
- затем `Unit offline` старой ноды и `Unit online` новой с тем же `node_id`.

### Корневая причина

`node_id` у слейва вычислялся как lower-32 от `ESP.getEfuseMac()`:
- `node_id = (uint32_t)(mac & 0xFFFFFFFFu)`.

На двух устройствах совпали младшие 32 бита MAC, из-за чего:
- мастер (который индексирует/ищет ноды по `node_id`) считал это переподключением одного и того же юнита;
- в `StackMaster` новая сессия вытесняла старую;
- в списке/синхронизации оставалась только одна запись.

### Что сделано (диагностика и исправление)

#### 1) Явная диагностика конфликта `node_id` на master

В `StackMaster` добавлен warning-лог при конфликте `node_id`:
- показывается `unit_id`, старое/новое имя и IP.

Также в логи `Unit online/offline` добавлен `id: 0x...`, чтобы сразу видеть идентификатор ноды.

Это позволяет быстро отличить:
- нормальный reconnect (тот же узел),
- от конфликта двух разных слейвов с одинаковым `node_id`.

#### 2) Быстрый фикс генерации `node_id` на slave

`node_id` теперь считается как 32-битный hash (FNV-1a) от **всех 6 байт** eFuse MAC, а не от lower-32:
- используется hash по 48-битному `ESP.getEfuseMac()`;
- `node_id == 0` дополнительно защищён (заменяется на `1`).

Эффект:
- вероятность коллизии резко ниже;
- кейс с совпавшими lower-32 больше не воспроизводится в типичном сценарии.

Важно:
- после этой правки `node_id` у слейвов меняется;
- если где-то сохранены привязки по `node_id` (remote display slots, rules, remote sources), их может понадобиться пересохранить/перевыбрать.

## Ускоренная первичная синхронизация слейва (bootstrap sync, без залпа)

### Зачем это понадобилось

После `Unit online` хотелось получать данные заметно быстрее (web/дисплей/списки), не дожидаясь долгого round-robin по всем нодам.

Но отправка залпа всех `CmdGet` сразу — плохой путь:
- создаёт конкуренцию `pending`;
- повышает риск starvation/долгих зависаний отдельных feature;
- это уже приводило к проблемам в stack sync ранее.

### Что сделано (текущая реализация)

Вместо burst-запросов после `Unit online` реализована **приоритетная bootstrap-синхронизация**:

- На `Unit online` нода ставится в bootstrap-очередь.
- Активная bootstrap-нода опрашивается с повышенным приоритетом.
- За тик отправляется **один запрос одной feature** (как и в обычном round-robin).
- Используется более частый интервал для bootstrap.
- После завершения bootstrap система возвращается к обычному round-robin.

То есть ускорение достигается не залпом, а:
- более частым тиком;
- приоритетом только что подключившейся ноды.

### Очередь bootstrap для нескольких нод

Добавлена очередь bootstrap (до `StackMaster::MAX_SESSIONS` нод):
- если несколько слейвов подключились почти одновременно, они не перетирают bootstrap друг друга;
- bootstrap выполняется по очереди;
- при `offline` нода удаляется из активного bootstrap или очереди.

Это особенно важно при старте мастера, когда в сеть одновременно возвращаются 2+ слейва.

### Логика завершения bootstrap

Bootstrap для ноды завершается, если:
- для ноды уже достигнут `Sync slave unit complete` (по логике inventory/caches), и выполнен минимум один проход bootstrap;
- либо истёк таймаут bootstrap;
- либо нода ушла offline.

Уточнение (после практики с 2+ слейвами):
- bootstrap handoff на следующую ноду не должен задерживаться из-за тяжёлых feature (`Ports`, `TempSensors`);
- для быстрого переключения достаточно:
  - `Sync slave unit complete` по core-инвентарю,
  - и факта отправки bootstrap-запросов по core-feature (`sockets/lights/security/prearm/thermo/septic/tanks/meteo/watering/avr/leak`);
- `Ports` / `TempSensors` продолжают догружаться обычным round-robin и не блокируют старт bootstrap для следующего слейва.

### Текущие тайминги / тюнинг (по состоянию на сейчас)

- Обычный polling:
  - `kStackPollMs = 2000`
- Bootstrap polling:
  - `kStackBootstrapPollMs = 250`
  - `kStackBootstrapTimeoutMs = 15000`
  - `kStackBootstrapPasses = 2`

Практика:
- это заметно ускоряет первичную доступность данных после `Unit online`;
- при этом не возвращает проблему “залпа запросов”.

### Debug-логи bootstrap (отключаемые)

Добавлен compile-time флаг:
- `STACK_BOOTSTRAP_DEBUG_LOGS` (в `src/app.cpp`)

По умолчанию:
- `0` (выключено)

Если включить:
- будут `DEBUG`-логи по bootstrap-очереди и прогрессу:
  - добавление/удаление из очереди;
  - старт/сброс активной bootstrap-ноды;
  - `feature/pass`;
  - `request skipped` (например, если feature ещё pending).

Это удобно для диагностики “почему bootstrap идёт медленно” без зашумления релизных логов.

### Что изменилось в поведении `Unit online`

Раньше:
- на `Unit online` отправлялась пачка `request*` почти по всем feature сразу.

Теперь:
- пачка на `Unit online` убрана;
- вместо неё запускается bootstrap sync queue.

Плюс:
- `sendSecurityStateToNode_()` остаётся сразу (это отдельная важная команда состояния, не часть bootstrap inventory).

### Диагностика в будущем (если снова “долго синхронизируется”)

Проверять по шагам:
1. Есть ли `Bootstrap sync start: ...` и затем `Bootstrap sync done: ...` (или `timeout`).
2. Есть ли `Sync slave unit ...` / `Sync slave unit complete: ...`.
3. Нет ли повторяющихся конфликтов `Duplicate unit_id conflict`.
4. Если включён debug bootstrap:
   - не застревает ли на одном feature (`request skipped` / pending),
   - идёт ли рост `pass`.
5. Не слишком ли жёсткие тайминги для конкретной сети/нагрузки (при необходимости поднять `kStackBootstrapTimeoutMs` или ослабить `kStackBootstrapPollMs`).

### Важные ограничения / замечания

- Bootstrap сейчас ускоряет только первичный прогрев кэшей после `Unit online`; дальше работает обычный round-robin.
- Для тяжёлых feature (`Ports`, page-based) bootstrap не отменяет page-based логику, а просто даёт им приоритет раньше.
- Быстрый hash по MAC снижает риск коллизий, но не заменяет идею явного `node_id override` в конфиге (если понадобится жёсткое управление ID в больших установках).
